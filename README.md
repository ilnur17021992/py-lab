# Правила разработки и архитектурные стандарты проекта py-lab

Настоящий документ определяет стандарты проектирования, написания кода и внесения изменений в проект **py-lab**. 
Цель данных правил — исключить накопление технического долга, не допускать появления «быстрых костылей» (hacky hotfixes) и гарантировать, что любое изменение реализуется на уровне зрелого сеньорского проектирования (Clean Code, Single Source of Truth, Accessibility, Robust Layouts).

---

## 1. Архитектурная парадигма: Zero-Build ES Modules

1. **Браузерная нативность**: проект работает без шага сборки (no bundler / zero-build). Используются стандартные модули ES6 (`import` / `export`, `<script type="module">`).
2. **Запрет скрытых зависимостей**: нельзя внедрять синтаксис, требующий Babel/Webpack/Vite (например, CommonJS `require()`, JSX, TypeScript-типы в `.js`), если в проект явно не введен пайплайн сборки.
3. **Изоляция модулей**: каждый модуль в каталоге `js/` решает ровно одну задачу (Single Responsibility Principle) и не загрязняет глобальную область `window`, за исключением согласованных точек расширения.

---

## 2. Единый источник правды для стилей (Design Tokens First)

Главная причина визуального регресса и разваливающейся верстки — дублирование размеров и цветов в разных файлах.

1. **Централизация в `styles/tokens.css`**:
   - Все глобальные размеры (высота шапки, высота терминала, ширина сайдбара), палитра цветов, радиусы скруглений, тени и шрифты объявляются **только** в `:root` файла `styles/tokens.css`.
   - *Плохо:* прописать в компоненте `height: 60px;` или `background: #ff6b00;`.
   - *Хорошо:* `height: var(--nav-height, 60px);`, `background: var(--primary);`.
2. **Категорический запрет `!important`**:
   - Использование `!important` является признаком капитуляции перед специфичностью селекторов. Если стиль не применяется, необходимо исправить каскад или структуру классов, а не форсировать свойство флагом.
3. **Семантическая палитра**:
   - Цвета состояний должны использовать токены: `--accent-green` (успех), `--accent-cyan` (информация/выделение), `--accent-warning` (ожидание), `--accent-red` (ошибки/остановка). Никаких случайных hex-значений в коде компонентов.

## 3. Разделение ответственности: CSS против JavaScript

1. **JS управляет состоянием, CSS управляет отображением**:
   - JavaScript должен манипулировать CSS-классами (`.collapsed`, `.active`, `.resizing`, `.loading`, `.saving`), а не накладывать микро-стили через `element.style.*`.
2. **Очистка инлайн-стилей при переключении состояний**:
   - Если элемент переходит в предопределенное состояние (например, `.collapsed`), JavaScript **обязан очистить конфликтующие инлайн-стили**:
     ```javascript
     // Сеньорский подход:
     element.classList.add('collapsed');
     element.style.height = ''; // Освобождаем инлайн-стиль, управление передается CSS-токену
     ```
   - *Почему это критично:* оставленный инлайн-стиль перебивает CSS-правила класса и ломает адаптивность или расчет высоты.
3. **Динамический расчет геометрии без магических чисел**:
   - Если JS рассчитывает границы перетаскивания (drag resize), минимальная и максимальная высота должны считываться из DOM (`element.offsetHeight`, `getBoundingClientRect()`) или вычисляться от размеров окна, а не задаваться жестко зашитыми константами вроде `const COLLAPSED_HEIGHT = 34`.

## 4. UI Kit: Доступность и запрет блокирующих нативных вызовов

1. **Полный запрет синхронных браузерных диалогов**:
   - Категорически запрещено использовать `window.alert()`, `window.confirm()`, `window.prompt()`. Они блокируют поток выполнения браузера, прерывают фоновые воркеры и визуально не соответствуют теме проекта.
2. **Использование модуля `js/ui/components/dialogs.js`**:
   - Подтверждение опасных действий: `await showConfirmDialog(title, message, options)`.
   - Ввод данных пользователем: `await showPromptDialog(title, message, defaultValue, options)`.
   - Уведомления и ошибки: `await showAlertDialog(title, message, options)`.
3. **Стандарты доступности модальных окон**:
   - Любая модалка должна реализовывать:
     - **Focus Trap**: фокус при нажатии `Tab` и `Shift+Tab` циклирует только внутри активного окна.
     - **Закрытие по клавише `Escape`** и клику по оверлею (`backdrop`).
     - **Возврат фокуса** на элемент, инициировавший открытие окна, после его закрытия.
4. **Всплывающие уведомления (Toasts)**:
   - Ненавязчивая обратная связь (сохранение файла, копирование кода, экспорт в ZIP, ошибки компиляции) выводится через `toast.js`:
     `toast.success(...)`, `toast.error(...)`, `toast.warning(...)`, `toast.info(...)`.

## 5. Изоляция вычислений: Pyodide Web Worker

1. **Тяжелые задачи — вне главного потока**:
   - Компиляция, запуск Python-кода, автоформатирование и линтинг AST выполняются **исключительно в Web Worker** (`js/worker/runner.worker.js`). Главный поток интерфейса (UI thread) всегда должен оставаться отзывчивым (60 fps).
2. **Асинхронный мост сообщений (`WorkerBridge`)**:
   - Связь с воркером строится на строго типизированных событиях (`stdout`, `stderr`, `request-input`, `finished`, `status`).
3. **Интерактивный ввод (`input()`)**:
   - Перехват Python `input()` реализован через асинхронный диалог с промисом `WorkerBridge.sendInputResponse()`. Никаких синхронных ожиданий на главном потоке.
4. **Уборка слушателей (No Memory Leaks)**:
   - Любые подписки на события (`addEventListener`) для разовых операций исполнения должны гарантированно отписываться (`removeEventListener`) в блоке завершения/ошибки.

## 6. Верстка и геометрия: правило 0px Gaps и устойчивые скроллбары

1. **`box-sizing: border-box` везде**:
   - Любые панели, заголовки и терминалы должны идеально прилегать друг к другу.
   - Если родительский контейнер имеет границу (`border-top: 1px`), дочерний элемент при сворачивании должен учитывать эту границу, чтобы под ним не образовывалось темных зазоров или двойных линий.
2. **Flexbox и скроллируемые области**:
   - Любой потомок Flex-контейнера с прокруткой (`overflow-y: auto`) обязан иметь `min-height: 0` (или `min-width: 0`), иначе flex-элемент не сжимается меньше размера своего контента, что вызывает расползание макета.
3. **Единый стиль скроллбаров**:
   - Кастомные скроллбары задаются глобально в `styles/base.css` для Webkit и Firefox (`scrollbar-width: thin; scrollbar-color: ...`).
   - Для предотвращения горизонтального дерганья контента при появлении полосы прокрутки используется `scrollbar-gutter: stable`.
4. **Полные состояния интерактивных элементов**:
   - Любая кнопка или интерактивный контрол обязаны иметь 4 оформленных состояния:
     - `:hover` — визуальный отклик при наведении.
     - `:focus-visible` — контрастная рамка фокуса для клавиатурной навигации.
     - `:active` — тактильное нажатие (`transform: scale(0.98)`).
     - `:disabled` — визуальное приглушение и `cursor: not-allowed; pointer-events: none;`.

## 7. Антипаттерны против сеньорского подхода

| Задача / Ситуация | ❌ Джуниорский костыль | ✅ Сеньорское архитектурное решение |
| :--- | :--- | :--- |
| **Разная высота шапки на страницах** | Подогнать `padding` или `margin` на одной из страниц пикселями наугад. | Вынести `--nav-height: 60px;` в `tokens.css`, привязать шапку и высоту рабочего пространства `calc(100vh - var(--nav-height))` к токену. |
| **Зазор под терминалом при сворачивании** | Добавить `!important` или подогнать высоту `height: 33px;`. | Устранить двойной border, в классе `.collapsed` задать `height: var(--terminal-header-height)`, а в JS очистить инлайн-стиль `style.height = ''`. |
| **Подтверждение удаления файла** | Вызвать нативный `if (confirm("Удалить?"))`. | Вызвать асинхронный стилизованный `const confirmed = await showConfirmDialog(...)` с клавиатурным фокусом. |
| **Стиль не перебивается каскадом** | Написать свойство с `!important`. | Разобраться в специфичности селекторов, объединить дублирующиеся стили в компонентный файл (`styles/buttons.css`). |
| **Уведомление об успешном действии** | Вызвать `alert("Сохранено!")` или добавить статичный `div` в разметку страницы. | Вызвать глобальный сервис `toast.success("Проект успешно сохранен")`. |
| **Сохранение состояния в LocalStorage** | Запись «сырых» строк без обработки исключений в произвольные ключи. | Изолированное хранилище с префиксом `learn_py_*` и обязательным блоком `try/catch` на случай QuotaExceeded или Privacy Mode. |

## 8. Чек-лист перед сдачей любой правки (Definition of Done)

Перед тем как считать задачу выполненной, проверьте код по следующим пунктам:

- [ ] **Никаких новых магических чисел:** все размеры и цвета привязаны к `tokens.css`.
- [ ] **Никаких `!important`:** каскад чистый и предсказуемый.
- [ ] **Никаких нативных `alert/confirm/prompt`:** используются компоненты из `dialogs.js` и `toast.js`.
- [ ] **Отсутствие зазоров и смещений:** элементы прилегают встык, адаптивная верстка не ломается при ресайзе окна.
- [ ] **Интерактивные состояния:** проверены hover, focus-visible, active и disabled.
- [ ] **Очистка ресурсов:** таймеры, анимационные кадры (`cancelAnimationFrame`) и слушатели событий удаляются при размонтировании/завершении.
- [ ] **100% сохранение функционала:** все существующие сценарии пользователя работают без регрессий.

## 9. Правила добавления и редактирования контента (Уроки, Разделы, Манифест)

Вся образовательная база уроков хранится по принципу **Content-as-Data**: каждый урок представляет собой независимый Markdown-файл в папке `content/topics/`, а реестр тем ведётся в `content/manifest.json`.

### 1. Создание нового урока (темы)
1. В каталоге `content/topics/` создайте файл `<id>.md` (название в `snake_case` или `kebab-case`, латиницей без пробелов, например `oop_basics.md` или `generators.md`).
2. Файл **обязан** содержать YAML Frontmatter в начале и две секции контента:
   ```markdown
   ---
   id: "oop_basics"
   title: "ОСНОВЫ ООП"
   category: "Продвинутый Python"
   icon: "🏛️"
   summary:
     - "Краткий тезис 1"
     - "Краткий тезис 2"
   ---

   ## Теория

   <h3>Подзаголовок теории</h3>
   <p>Пояснение темы. Для выделения терминов используйте теги <code>код</code>, <strong>жирный</strong>.</p>

   ## Примеры кода

   ### Название первого интерактивного примера

   Краткое описание того, что демонстрирует пример кода.

   ```python
   # Рабочий запускаемый код Python
   class User:
       def __init__(self, name):
           self.name = name

   print(User("Alice").name)
   ```
   ```

### 2. Создание или привязка к разделу (Категории)
- Раздел определяется полем `category` во Frontmatter каждого урока.
- Если вы вводите **новый раздел**, просто укажите его понятное название в `category` (например, `"Асинхронность"`, `"Алгоритмы"`). При парсинге уроков каталог автоматически сгруппирует темы и создаст новый фильтр/раздел в UI.
- Соблюдайте единообразие существующих категорий (например: `Основы`, `Типы данных`, `Управление потоком`, `Функции и модули`, `Инженерия и качество`, `Продвинутые концепции`).

### 3. Регистрация в реестре `content/manifest.json`
После создания файла урока обязательно зарегистрируйте его `id` в файле `content/manifest.json` в массиве `topics`:
```json
{
  "version": "2.1.0",
  "description": "...",
  "topics": [
    "basics",
    "types",
    "...",
    "oop_basics"
  ]
}
```
*Порядок в массиве `topics` определяет очередность отображения уроков в интерфейсе.*

### 4. Обязательное версионирование при изменении или добавлении уроков
- **Каждое изменение, правка или добавление урока ОБЯЗАНО сопровождаться инкрементом версии в `content/manifest.json`** (`"version": "2.x.x"` по SemVer).
- **Почему это критично:** браузеры агрессивно кэшируют статические файлы. Механизм загрузки `CourseService` считывает `version` из манифеста и автоматически запрашивает файлы тем с хэш-параметром `?v=${version}`. Без поднятия версии пользователи продолжат видеть старый кэш или ошибки 404 на продакшене.

### 5. Требования к хостингу и статике
- В корне репозитория всегда должен находиться файл `.nojekyll`. Без него GitHub Pages интерпретирует папки через движок Jekyll и скрывает исходные `.md`-файлы (преобразуя их в `.html` и возвращая 404 на `fetch()`).
